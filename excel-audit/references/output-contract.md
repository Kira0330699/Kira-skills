# 审计输出和修复要求

## 结论先行

按用户选定的形式交付。小范围问题可以直接在对话说明，不默认另建工作簿、报告、图表或新工作表。用户要求可保存报告时再生成相应交付物。

先说明：核查了什么、哪些关键结果受影响，以及当前结论。建议用以下自然语言状态，不创建看似权威的评分或认证：

- **发现需要修正的问题**：有已证实且影响结果或理解的问题。
- **待核实**：决定性口径、来源、运行时或依赖不可得，无法得出相应结论。
- **已检查范围内未发现问题**：限定实际覆盖，不能表述为“整个Excel无误”。

不同区域可以状态不同。例如“收入计算已复核，外部查询刷新状态待核实”。小问题不必阻止与其无关的结果使用，关键口径问题则说明具体受影响结论。

## 问题记录

多项问题用表格；单个问题用清楚的段落即可。每项应有：

| 字段 | 要求 |
| --- | --- |
| 位置 | 文件/版本、工作表、单元格或范围；命名范围、透视表、图表或查询可用准确对象名 |
| 问题 | 描述观察到的错误行为或冲突，不只写“公式不对” |
| 证据 | 实际值/公式/筛选条件/源标签；只展示解释所需的数据 |
| 应有结果 | 基于明确口径的正确计算或预期行为；口径待定时列为待确认，不伪造精确答案 |
| 影响 | 受影响金额、比例、期间或结论；不能量化时说明原因，不猜数 |
| 建议或修复 | 具体引用、范围、定义或计算如何调整；修复状态与建议分开 |

同一根因影响大量单元格时，合并为一项，给代表位置和全部影响范围。不要将同一问题拆成大量记录制造严重程度。

## 优先级

按照用户业务影响排序，避免把数值大小作为唯一标准：

- **高**：关键结果使用错误期间、范围或数据；系统性漏数/重复；核心公式、模型驱动或分母错误。指出哪些输出暂不应依赖。
- **中**：局部计算或分类错误、关键标签歧义、刷新/引用问题，已能明确其影响范围。
- **低**：不改变结果的局部展示、可读性或维护问题。
- **待核实**单独标识证据状态，必要时同时说明潜在影响；不要把未经证实的怀疑列为已发现错误。

不要为了套模板强行凑齐每个级别，也不要把所有格式问题都报出来。能改变解释或后续操作的问题才值得进入主要发现。

## 覆盖与限制

用简短记录说明：

- 审查的文件版本、工作表、关键结果及范围。
- 全量扫描、逐项复算、公式族抽查与业务样本各覆盖什么。
- 独立控制来源、计算方法和必要容差。
- 是否实际使用目标引擎重算、刷新、情景测试或视觉核验。
- 未验证的外部依赖、宏/UDF、保护区域、对象或缺失资料，以及它们影响哪些结论。

没有原始资料只能验证内部一致性时，要明确内部算平不等于底层业务真实、完整或符合原始口径。审计发现不等同于法定审计意见。

保留可复现计算和来源定位，使用宿主支持的文件或单元格引用。不要暴露无关明细、个人数据、凭证或连接密钥。

## 授权修复的交付

1. 在授权范围内修正已证实问题，保留来源和业务定义，不用硬填差额代替修复根因。
2. 对影响结果的口径有歧义时先完成可独立推进的部分；必要的定义选择由用户决定。
3. 检查受影响依赖，包括汇总、透视、图表、文字结论和截图，避免“数改了、结论未改”。
4. 对数据与公式重新复核；工具支持时重算并检查视图。若不能完成某项目标引擎验证，明确说明。
5. 对照原文件检查范围外变化，以及宏、对象、验证、命名范围和格式保留情况。可能损失原生功能时选择更保真的方式，不能悄悄导出缩水文件。
6. 交付用户可打开的修复版本，说明主要改动、验证与剩余限制。中间脚本或测试副本无需作为交付物，除非用户要求。
